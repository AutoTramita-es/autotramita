## 1. Verdict
**Not ready to authorize packet F1 (before the H1–H6 follow-up above; remaining gates: acceptance of ADR-010/011, AT-03 reconciliation for F3a, G6 execution order).** The architecture is sound and AT-03 business rules are well covered, but three blockers (G5-01 to G5-03) would make the first migration or the first RLS test wrong, and several shared conventions are still open. All blockers are decisions or documentation, not research, and can be closed in one pass.

## 2. Findings
| ID | Sev. | Finding | Evidence | Proposed resolution |
|---|---|---|---|---|
| G5-01 | P0 | **Role model contradicts ADR-002.** The provisioning script creates one role per environment and makes it the **database owner**. If the same role runs migrations it owns every table, and a table owner bypasses RLS unless `FORCE ROW LEVEL SECURITY` is set; ADR-002 also requires the application role not to be owner. One role cannot be both migrator and runtime. | `provision-postgres.py:47-57` (`CREATE DATABASE … OWNER user`); ADR-002 | Per environment four roles: `*_owner` (owns schema, runs Alembic, no app use), `*_app` (runtime, `NOBYPASSRLS`, not owner, grants only), `*_worker` (Celery, own tenant context), `*_platform` (cross-tenant review path, see G5-05). `REVOKE ALL ON SCHEMA public FROM PUBLIC`; default privileges per owner; FORCE RLS on every tenant table. Update the script before it is ever run. |
| G5-02 | P0 | **Membership lookup vs RLS bootstrapping.** The tenant is resolved from the user's membership, but `tenant_memberships` is tenant-scoped with RLS keyed on `app.tenant_id`, which is not set yet when the lookup happens. | ADR-002, ADR-003, AT-03 #24 | Two-step context: (1) `app.user_id` set transaction-locally; `tenant_memberships` and `membership_branches` get an extra policy `user_id = current_setting('app.user_id')` for the user's own rows only, SELECT only; (2) after server validation set `app.tenant_id` and `app.branch_ids`. Never a SECURITY DEFINER shortcut that returns other users' rows. Cover with cross-tenant negative tests. |
| G5-03 | P0 | **Accepted ADRs are stale against later owner decisions.** ADR-001 still says S3-compatible storage and "OIDC provider to be selected"; ADR-005 says private S3 with short-lived scoped access. Later decisions chose shared Nextcloud via WebDAV/OCS with service accounts and Keycloak. The master blueprint records this, but ADR-008 requires explicit superseding or amendment, not silent drift. | ADR-001, ADR-005, [DNS doc](../DNS-NEXTCLOUD-MAIL.md) | Draft **ADR-010** (Keycloak as identity provider, `users.auth_subject` = Keycloak `sub`) and **ADR-011** (documents on shared Nextcloud; supersedes the S3 clause of ADR-001, amends ADR-005: application-issued short-lived download links, metadata in PostgreSQL, ClamAV quarantine). Both Proposed until you accept them. |
| G5-04 | P1 | **Session and active context.** AT-03 #12/#19 require immediate revocation, per-session active tenant/branch, device list and remote logout. Putting tenant/branch in token claims would make revocation and tenant switching stale. | AT-03 #12, #19, #24; final design §5 | Application-owned `user_sessions` table (id, user, device info, active tenant/branch, last activity, revoked_at) checked on every request; Keycloak proves identity only. Access tokens short-lived. Proposed timings from final design (30 min idle, 12 h web) stay pending your approval. |
| G5-05 | P1 | **Cross-tenant platform path is undefined.** ADR-002 allows it only "narrowly scoped and audited"; AT-17 reviewers must read verification records of tenants that are not ACTIVE. | ADR-002, ADR-009 | `*_platform` role, `NOBYPASSRLS`; policies allow it only through a `platform_grants` row (reviewer, scope, tenants/queues, expiry) matched against `app.actor_id`; every use writes an AuditEvent in the same transaction. No arbitrary tenant switching; support access is a separate time-boxed `SupportAccessGrant` (AT-03 #20). |
| G5-06 | P1 | **AuditEvent shape.** ADR-002 says every tenant table has non-null `tenant_id`, but platform actions (verification review, owner-transfer approval) have no single tenant context and some predate the tenant row's activation. Append-only is a requirement, not a mechanism. | ADR-009, AT-03 #21 | Single `audit_events` table with `tenant_id` nullable plus `scope` (`TENANT`/`PLATFORM`); RLS shows tenant events to that tenant, all to platform role; `REVOKE UPDATE, DELETE` from every runtime role plus trigger guard; written in the business transaction; hash chaining optional later. |
| G5-07 | P1 | **Routing and naming mismatch.** DNS plan is host-based (`clientes.`, `partners.`, `admin.`, `auth.`, `api.`); the design route registry is path-based on one host (`/empresa`, `/cliente`, `/gestoria`, `/ingenieria`, `/administracion`). Also "partners" means dealerships in the hostnames and Nextcloud tree (`Partners/{partner_uuid}`), but ADR-006 uses "partners" for authorized gestorías. | DNS doc, DESIGN-ROADMAP §8, ADR-006 | Decide one model. Recommendation: one web origin `autotramita.es` with path workspaces (one Next.js app, one cookie scope, fewer CORS and CSRF surfaces); keep `api.`, `auth.`, `webhooks.`, `admin.` as separate hosts; rename dealership terms to **empresa/concesionario** and reserve **partner/colaborador** for gestorías and engineers; rename Nextcloud root `Partners/` to `Tenants/{tenant_uuid}` before provisioning. |
| G5-08 | P1 | **Shared API conventions still open** (ADR-004: error schema, pagination, rate limits). F1 must ship them. AT-03 API sketch also uses `404` for invisible resources and `PUT/PATCH` with optimistic version. | ADR-004; AT-03 final §7 | Defaults to approve: errors as RFC 9457 `application/problem+json` with stable `code`; cursor pagination (`limit`, `cursor`, no invented totals); `Idempotency-Key` header on consequential POST with 24 h key retention; `If-Match`/`version` for updates; per-route rate limits configurable, values set at F1; tenant in path is never authority. |
| G5-09 | P1 | **AT-03 documents not yet reconciled.** Final design is PROPOSED; ADR-009, `tenant-branch.md`, `tenant-membership.md` still lack delegated MANAGER invitations, platform approval of OWNER changes, BR-0001 codes and session scope (its own §9 lists this). Defaults awaiting approval: granular permission matrix, 30 min idle / 12 h session, 24 h support and export links. Central MFA (R07) is proposed, dealership MFA optional per #18. | AT-03 final §9 | Reconcile and mark the final design Approved before F3a; F1/F2 can proceed without it. |
| G5-10 | P2 | **Shared host risks** (do not block local F1, block live use). Same Cloudflare token in all six token files with broad rights; existing PostgreSQL PUBLIC grants on unrelated databases; shared Postgres, Nextcloud and Traefik are common failure and trust boundaries; backup and restore are undefined; DEV mail not network-isolated. | [DNS doc](../DNS-NEXTCLOUD-MAIL.md) | F1 runs against a throwaway local/CI PostgreSQL only. Before first live deploy: split and scope tokens, review PUBLIC grants, define backup/restore drill, isolate DEV mail. |
| G5-11 | P2 | **Tooling not pinned.** Host has Python 3.10 (ADR-001 stack and Pydantic v2/SQLAlchemy 2 assume modern Python), no `uv`, no Flutter, Node present; shared PostgreSQL is 16.16; CI platform not chosen (repo is on GitHub). | environment check | Propose Python 3.12, `uv` with lockfile, PostgreSQL 16 service container in GitHub Actions, Ruff + mypy + pytest as in ADR-001; Next.js/Flutter versions pinned at their own packets. Install nothing before authorization. |
