# AutoTramita.es — Development guide (phase F1)

Scope: the F1 foundation only (toolchain, configuration, database layer, migrations, RLS tests, API conventions, rate limiting, health, OpenAPI, CI). There are no business tables, no authentication and no deployment. See [G6-EXECUTION-ORDER.md](G6-EXECUTION-ORDER.md) for what F1 may and may not touch.

## Prerequisites
Use Python **3.12.16** and uv **0.13.9**. Install uv from the versioned official release, then install the pinned Python:

```sh
curl --proto '=https' --tlsv1.2 -LsSf https://releases.astral.sh/github/uv/releases/download/0.13.9/uv-installer.sh | sh
uv --version                 # must report 0.13.9
uv python install 3.12.16
```

`pyproject.toml` enforces uv 0.13.9; commands fail rather than silently using another version. `.python-version` selects Python 3.12.16. Runtime requirements and the `dev` dependency group remain separate; `uv.lock` fixes the resolved versions. OpenTelemetry API and SDK are runtime dependencies for the future integration point; no instrumentation or exporter is configured in F1.

The locked direct runtime versions include Alembic 1.20.1, FastAPI 0.165.0, OpenTelemetry API/SDK 1.45.2, psycopg 3.3.9, Pydantic 2.14.4, pydantic-settings 2.16.3, redis client 8.2.0 and SQLAlchemy 2.1.9. The dev group locks HTTPX 0.28.1, mypy 2.4.1, pytest 9.2.0 and Ruff 0.17.6.

Also install Docker (disposable test containers, client generation) and Node 20 (TypeScript client check).

```sh
uv sync --locked          # create .venv from uv.lock
uv run --locked ruff check .
uv run --locked ruff format --check .
uv run --locked mypy
```

## Test infrastructure (disposable, never the shared server)
Integration tests need their own PostgreSQL 16 and Redis. Use throwaway containers bound to localhost with a random password; **do not point tests at the shared `postgres` container**.

```sh
PW=$(openssl rand -hex 16)
docker run -d --rm --name at-f1-pg -e POSTGRES_PASSWORD=$PW -p 127.0.0.1:55432:5432 \
  --tmpfs /var/lib/postgresql/data postgres:16-bookworm
docker run -d --rm --name at-f1-redis -p 127.0.0.1:56379:6379 redis:7.4-alpine
export TEST_PG_ADMIN_URL=postgresql://postgres:$PW@127.0.0.1:55432/postgres
export TEST_REDIS_URL=redis://127.0.0.1:56379/15
uv run pytest -q
```

Without these variables integration tests are skipped locally; when `CI` is set a missing variable fails the run. Tests create and drop their own databases and roles.

## Checks run in CI
`.github/workflows/ci.yml` is verification only: no deployment, no production secret, no privileged runner, `permissions: contents: read`, `pull_request` (never `pull_request_target`) so fork code never sees secrets. It runs on pushes and pull requests to `dev` and `main` with three jobs:

- **Lint, types, tests**: PostgreSQL 16 and Redis 7 service containers (pinned by digest, throwaway credentials, health checks plus an explicit wait step), `uv sync --locked`, Ruff lint and format, mypy, the full pytest suite with a junit summary that fails the job if any test is skipped, failed or errored, a named step for owner migrations (upgrade head, downgrade base, upgrade again, role SQL applied twice, migration refused for non-owner roles), the OpenAPI drift check and the TypeScript and Dart generation check.
- **Secret scan**: gitleaks v8.21.2 (image pinned by digest) over the full history. Exceptions are exact fingerprints in `.gitleaksignore`.
- **Dependency audit**: `pip-audit==2.10.1` against the locked requirements.

Everything is pinned: actions by commit SHA, runner `ubuntu-24.04`, uv 0.13.9, Python 3.12.16, Node 20, container images by digest. `tests/test_ci_workflow.py` guards these properties. Dependabot is not configured (a separate owner decision). When a pin needs updating, look up the new SHA or digest, change it in the workflow (and `openapi/check-clients.sh` for the Dart generator), and let CI prove it.

## Layout
- `app/core/` configuration, database layer and request context, role model, errors, pagination, idempotency, versioning, rate limiting, logging.
- `app/api/` application factory, error handlers, middleware, OpenAPI, `v1/` routers (health only in F1). ASGI entry: `app.api.main:app`.
- `migrations/` Alembic, run as the **owner** role only; migration state lives in the `schema_migrations` schema, which runtime roles cannot read.
- `scripts/db/harden.sql` schema hardening applied after roles are created.
- `openapi/openapi.json` committed contract; regenerate with `uv run python -m app.api.export_openapi`.

## Conventions
- **Database roles** (per environment): `owner` owns objects and runs migrations; `app` (API), `worker` (Celery) and `platform` (cross-tenant review, no access by default) never own tables and never have `BYPASSRLS`. Tenant tables use `ENABLE` plus `FORCE ROW LEVEL SECURITY`, policies with `USING` and `WITH CHECK`, and composite `(tenant_id, id)` keys.
- **Settings** (`app/core/config.py`): four separate PostgreSQL role configurations, never derived from one another. `app` (API runtime) is `POSTGRES_USER`/`POSTGRES_PASSWORD` and is the only required role; `owner` (migrations only) is `APP_DB_OWNER_USER`/`APP_DB_OWNER_PASSWORD`; `worker` is `APP_DB_WORKER_USER`/`APP_DB_WORKER_PASSWORD`; `platform` is `APP_DB_PLATFORM_USER`/`APP_DB_PLATFORM_PASSWORD`. Shared: `ENVIRONMENT` (`dev`, `prod` or `test`, required), `POSTGRES_HOST`, `POSTGRES_PORT` (default 5432), `POSTGRES_DB`, `REDIS_URL`. A user without a password (or the reverse), an empty value, or two roles with the same user name or password is rejected; an unconfigured role raises `RuntimeError` instead of falling back. `Settings.database_url(role)` returns an escaped URL as `SecretStr`; engines belong to the DB layer. The Redis URL, passwords and URLs are `SecretStr`, validation errors carry no input, and `Settings.redis_url` returns the clear string only for creating the client. No `.env` or secrets file is read and nothing connects at import. In the existing compose file the worker container still receives its role through `POSTGRES_USER`/`POSTGRES_PASSWORD`; that contract is unchanged.
- **Engines** (`app/core/db.py`): `create_db_engine(settings, role)` builds a lazy engine for exactly one of `app` (default; `runtime` is the legacy alias), `worker`, `owner` or `platform`; an unconfigured role raises `RuntimeError` and never falls back. API code uses `app`, the worker uses `worker` with its own context, migrations use `owner`. `RequestContext` accepts only `UUID` values (`TypeError` otherwise).
- **Role SQL and migrations**: `scripts/db/harden.sql` (applied by `app.core.dbroles.harden`) is idempotent and is run against a disposable or explicitly provisioned database only, never by the F1 tooling against the shared server. `migrations/env.py` refuses to run (R02/R03) unless the connection is fresh (a caller-owned active transaction is rejected and left untouched, never committed or rolled back), the role is the expected owner when known (the engine path uses the configured owner; tooling may pass `config.attributes["expected_owner"]`), logs in as itself (no `SET ROLE`), owns both `schema_migrations` and `public`, has no superuser, BYPASSRLS, CREATEROLE, CREATEDB or REPLICATION attribute and is not a member of a role that does; only the owner role on a hardened database can migrate, and rejection runs one read-only catalog query and no DDL. The baseline holds technical objects only (the RLS context functions); there is no business table and no idempotency table in the migration chain. `tests/test_role_sql.py` is the evidence for AC03/AC04.
- **RLS harness** (`tests/rls_probe.py`, `tests/test_rls.py`, `tests/test_rls_harness.py`): owner-created, test-only parent/child/membership tables (UUID `tenant_id` NOT NULL, composite tenant FKs, ENABLE plus FORCE RLS, `USING` plus `WITH CHECK`) exercised through real app, worker and platform connections with synthetic tenants A and B. It is never migrated into the production schema. A failing negative test blocks all later tasks (CP05 security gate).
- **Request context**: always `session_scope(engine, RequestContext(...))`; it writes `app.user_id`, `app.tenant_id` and `app.branch_ids` with transaction-local `set_config`. Transactions are explicit (R01): `create_session_factory` disables autobegin and `session_scope` rejects any factory that does not, so a session outside the scope cannot run a statement. Do not commit inside the block (the scope commits at exit); an early commit, rollback or close ends the transaction and drops the context, and the session then rejects every further statement with `InvalidRequestError` rather than starting a new context-free transaction. Policies read it through `app_tenant_id()`, `app_user_id()` and `app_branch_ids()`.
- **Errors** (`app/core/errors.py`, `app/api/errors.py`) are RFC 9457 `application/problem+json` with `type`, `title`, `status`, `detail`, `code` and `request_id`. Codes are stable English UPPER_SNAKE_CASE (enforced; e.g. `VALIDATION_ERROR`, `VERSION_MISMATCH`, `IDEMPOTENCY_KEY_REUSE`) and `type` is `https://docs.autotramita.es/errors/<kebab-code>` (a planned documentation URI, not a claim that the page exists). Status mapping follows AT-01 §10a (400, 401, 403, 404 for missing or invisible, 409, 412, 413, 415, 422, 428, 429, 500, 503; 405 comes from the framework). Validation errors list only field names and static messages, never submitted values. The request id is a UUID (a valid incoming `X-Request-ID` UUID is kept, anything else is replaced). Use `AppError` subclasses.
- **JSON types** (`app/core/types.py`): derive models from `ApiModel` (snake_case, unknown fields rejected) and use `UtcDatetime` (timezone required, normalized to UTC, `Z` suffix), `CurrencyCode` (checks the ISO 4217 format, three capital letters, not the full ISO 4217 registry) and `DecimalString` (exact decimal exchanged as a JSON string; floats rejected).
- **Pagination** (`app/core/pagination.py`): `limit` default 25, 1 to 100, no totals. Cursor = `base64url(payload).base64url(HMAC-SHA256)` signed with `CURSOR_SIGNING_KEY` (at least 32 bytes, optional setting; `CursorCodec.from_settings` fails closed without it). The payload binds tenant, filter hash, sort and last-row position; any mismatch or tampering is `400 INVALID_CURSOR`. Callers pass the unique `tie_breaker`, which must be the last sort field and is part of the signed binding. Without `CURSOR_SIGNING_KEY` no cursor can be created or accepted (no default key, no unsigned cursor). Cursor values must be bound as query parameters.
- **Optimistic locking** (`app/core/versioning.py`): resources expose an integer version as `ETag: "<version>"`; updates send `If-Match`. Missing is `428 PRECONDITION_REQUIRED`, malformed is `400 INVALID_IF_MATCH`, stale is `412 VERSION_MISMATCH` (`UPDATE ... WHERE version = :expected`, then `ensure_updated(rowcount)`).
- **Idempotency** (`app/core/idempotency.py`, AT-01 O03): `Idempotency-Key` is required on consequential POST (400 if missing or invalid, at most 128 characters, a UUID v4 is recommended), kept 24 hours, scoped by actor + tenant + operation + key. The fingerprint is SHA-256 over method, operation and canonical JSON of the body (`app/core/canonical.py`: sorted keys, compact, UTF-8, numbers as parsed; non-JSON bodies are hashed raw). The caller is re-authorized on every request including replays; a different payload or an in-flight duplicate is `409` (`IDEMPOTENCY_KEY_REUSE`, `IDEMPOTENCY_IN_PROGRESS` with `Retry-After`); an identical finished request returns the stored response without running the handler. Everything runs in one PostgreSQL transaction under an advisory lock, so the business change and the stored response commit together or not at all. The `idempotency_keys` table is not in the migrations (owner decision); F1 tests create it as a disposable fixture (`tests/idempotency_fixture.py`) and Redis plays no role. Known limit: nothing prevents a future route from forgetting `authorize`; business routers must pass the real authorization check.
- **Rate limiting** (`app/core/ratelimit.py`, AT-01 O02/O18, F1-T07): Redis 7, approximate Sliding Window Counter in one atomic Lua script that uses the Redis server clock. Time is split into buckets of the window length (60 s); `estimate = previous_count * (1 - elapsed / window) + current_count` and a request passes if `estimate + 1 <= limit`. It is an approximation (it assumes requests were spread evenly over the previous bucket), in return for two counters per limit. Defaults per minute, from `RATE_LIMIT_*`: public 60 per IP, authenticated 300 per user, tenant 3000, upload 30 per user, export 5 per user; `/api/v1/health` is exempt. Owner-approved semantics: all limits that apply to a request are checked together and counted only if every one allows it (all or nothing); a denied request (429) consumes no quota; `Retry-After` is the longest wait over the blocking limits, in whole seconds, at least 1. Keys are `rl:<environment>:<policy>:<hash of identity>` (never raw IPs or ids); actor identities include the tenant. A client behind trusted proxies is resolved from `X-Forwarded-For` only when `TRUSTED_PROXY_HOPS` is set, using the entry the closest trusted proxy appended, otherwise the peer address; live proxy addresses are deferred. **Availability trade-off:** Redis connect and operation timeouts are 500 ms each, there is no retry and no local fallback, so a Redis failure answers limited requests with `503 RATE_LIMIT_UNAVAILABLE` and `Retry-After: 5` (security over availability). The old `RATE_LIMIT_FAIL_OPEN` switch was removed and the variable is ignored. A limited route without a configured limiter is also 503, never unlimited. The Keycloak and password-recovery values are reserved for F2. Routes using several limits use `rate_limits([Rule(policy, identity), ...])`; F1 has no upload, export or authenticated endpoints, tests use test-only routes.
- **Gitleaks exception (F1-T06)**: the secret scan flagged `KEY = "<synthetic UUID>"` in `tests/test_idempotency.py` (rule `generic-api-key`, commit `05c49be`, line 34). Review of the source confirmed a synthetic UUID used as the `Idempotency-Key` in a test, not a secret. The owner approved one exact-fingerprint entry in `.gitleaksignore` (history is not rewritten) and renaming the variable to `IDEMPOTENCY_TOKEN_A`. The renamed literal would have been flagged again, so the value is now built as `str(uuid.UUID(int=..., version=4))`, still a valid synthetic UUID v4, instead of adding a second exception. Rules, tool version and scan scope are unchanged; no other exceptions were added.
- **Health and observability** (`app/api/v1/health.py`, `app/core/health.py`, `app/core/telemetry.py`, F1-T08): the only public health route is the liveness probe `GET /api/v1/health` returning `{"status": "ok"}`. It answers from the process alone (it works when PostgreSQL, Redis or the limiter are down), is exempt from rate limiting and discloses no dependencies, versions or host names. The former public `/api/v1/health/ready` route was removed on owner decision (open decision O20: readiness is separated from liveness before going live); the PostgreSQL and Redis check remains as the internal function `check_dependencies`, which reports component names only. For that removal the owner allowed regenerating `openapi/openapi.json`, outside the usual T08 paths. OpenTelemetry is a hook only: `TelemetryMiddleware` opens one server span per request through the OTel API and is a no-op until a provider is passed to `set_tracer_provider`. There is no exporter, no credentials, no Sentry or external monitoring and no network call. Spans carry only the method, the route template (never raw paths or parameter values), the status code, the request id and the error type, and never query strings, headers, addresses, bodies or exception messages. Request ids and log redaction are reused unchanged.
- **OpenAPI contract** (`app/api/openapi.py`, `app/api/export_openapi.py`, `openapi/`, F1-T09): `uv run python -m app.api.export_openapi` writes `openapi/openapi.json` from the real FastAPI app (sorted keys, stable across runs, processes and environments; it needs no configuration); `--check` fails when the committed file is out of date. `info.version` comes from `API_VERSION` and must equal `pyproject.toml`; all paths are under `/api/v1/`. Every response declares `X-Request-ID`; 429 documents `Retry-After` and `RateLimit-*`, 503 documents `Retry-After`, 409 documents the optional `Retry-After` of an in-flight idempotent request. Validation errors (422) are documented and returned as `Problem`, so FastAPI's own validation schemas are removed. The contract currently exposes only the health route and the shared models `Health` and `Problem`; it makes no claim of business client coverage. Business routers reuse `PROBLEM_RESPONSES`. Client generation is checked, not committed: `./openapi/check-clients.sh` generates TypeScript with `openapi-typescript@7.13.0` (compiled with `typescript@5.6.3`, needs Node 20) and Dart with the Docker image `openapitools/openapi-generator-cli:v7.10.0` into a temporary directory that is deleted afterwards; CI runs it (AC13 stays partial until the final CI evidence of T10).
- **Never** put secrets, personal data or real documents in the repository, fixtures or logs.

## Rollback
F1 is not deployed and nothing here touches a shared environment, so rollback is local and reversible:
- **Code**: `git revert` the offending commit on `dev` (history is never rewritten); `main` only ever receives reviewed merges.
- **Database** (disposable or explicitly provisioned only): as the owner role, `alembic downgrade base` removes the baseline functions; `scripts/db/harden.sql` is idempotent and can be re-applied; test databases and roles are dropped by the tests themselves.
- **Disposable containers**: `docker rm -f at-f1-pg at-f1-redis`.
- **OpenAPI**: regenerate with `uv run python -m app.api.export_openapi` after reverting code.

## Known limits of F1
- The in-database context is set by the application; code that can run arbitrary SQL as a runtime role could set another tenant's context, so SQL is always parameterized and runtime roles have no DDL rights.
- `scripts/provision-postgres.py` has its own copy of the hardening statements and is not run by F1; align it with `scripts/db/harden.sql` before first use.
- The idempotency table is not part of the migrations (owner decision): a later phase must add it with the shape in `tests/idempotency_fixture.py`. Likewise there are no tenant or business tables.
- Authentication, Keycloak, the worker process and real tenants do not exist; tests use synthetic contexts and test-only routes. Readiness is not exposed publicly (open decision O20); live proxy addresses for `TRUSTED_PROXY_HOPS` are deferred.
- The rate limiter is an approximation by design and, if Redis is down, limited endpoints answer 503 (security over availability).
- `CurrencyCode` checks the ISO 4217 format only. The OpenAPI contract covers only the health route and the shared models.
- TypeScript and Dart generation is checked, not committed; npm transitive packages of the generator are not locked.
- Migration 0002 was removed from the chain on the basis of repository documentation that no persistent database was ever migrated, not of a check of the live databases.
- Keycloak, documents and deployment belong to later phases.
